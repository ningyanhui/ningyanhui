1. 本周执行摘要

Agent Memory 正在数据化

ClickHouse 11/13 发布 Loom：基于 ClickHouse 的共享代码索引与 Agent Memory，强调跨会话持久化及随代码变化校验。

判断：Data Agent 应把 SQL、Schema、执行计划、人工修正沉淀为可查询 Memory，而非只依赖向量库。

Text-to-SQL 进入 System 1 / 2 级联

LuthorSQL 11/13 提出本地 7B 快速门控，不确定时再升级强模型；论文报告约半数测试问题可本地处理并降低 API 成本。

判断：企业 Data Agent 可以用快模型+验证器控制成本与延迟。

MCP/Skill 开始进入分发治理层

FastMCP 4.2 在 11/13 加入实验性 Skills over MCP；MCP 2026-07-28 已转向无状态协议层。

判断：企业需要 Tool/Skill Gateway、Identity、Policy、Audit、Catalog，而非 Agent 直连数据系统。

Agent 已成为分析平台消费者

Doris Summit 2026 给出银行案例：Agent 通过 MCP 查询 Doris、读取受治理模型分数并解释风险。

判断：Data Platform 的接口对象从人/BI扩展到机器 Agent，权限、SLA、并发、审计需要重设计。

趋势：未来 1–3 个月最值得关注的不是“又一个 Agent Framework”，而是 Agent Workload 如何进入数据平台控制面：调度、权限、Tool/Skill、Memory、Trace、Evaluation、成本和生命周期形成闭环。

3. 深度分析

01 · LuthorSQL：本地 System 1

是什么：7B 非自回归 Text-to-SQL，用快速候选计划+validator 做门控，低置信度升级强 Agent。

相关性：Data Agent 可把强模型从“每次必调用”变成长尾兜底层。

  • 场景：BI 问答、内部数据门户、成本敏感 SQL Agent。
  • 路径：问题分类 → 本地 SQL → EXPLAIN/执行验证 → 强模型兜底 → 审计。
  • 风险：业务语义、权限、方言和 schema 分布会改变收益。
  • PoC：500 条真实问答，比较准确率、P95、Token、API 成本。

02 · MEM-SQL：把已验证 SQL 变成资产

存储查询模板、SQL blocks、业务概念→Schema 映射，并按证据决定是否查 Schema。

论文报告：HARE 上平均执行准确率 37.1%→50.0%，输入 Token -76.6%，平均延迟 -68.8%。

建议：Data Agent Memory 至少维护 Verified SQL / Join / Metric / Schema mapping / Feedback 五类结构化记忆。

03 · FastMCP 4.2：Skill 可分发

服务端 Skill Catalog 让 Skill 与 Tool 同处 MCP Server，客户端按需发现。

数据平台应用：Kafka 故障诊断、Flink Checkpoint、Doris SQL 治理、YARN OOM 恢复等可成为受治理 Skill。

边界：实验性扩展，不应把协议支持等同于生产治理完成。

04 · Doris：Agent 正式成为分析消费者

Summit 案例显示银行 Agent 通过 MCP 查询 Doris，读取受治理模型分数并解释风险。

架构：Semantic Layer + Row/Column Policy + MCP + SQL Audit + Lineage + Citation。

PoC：20 个业务问题，限制到 5–10 张治理表，记录身份、权限、SQL、来源列。

05 · ITOps Observability Studio

11/15 arXiv：数据访问、Schema、可视化、Trace 生命周期拆成专门 Agent，并统一工具接入。

启发：拆成 Kafka/Flink/YARN/DQ/Lineage Agent，由 Orchestrator 汇总证据。

风险：多 Agent 增加通信、权限与错误传播；必须有确定性 Policy/Approval。

06 · ClickHouse Loom

11/13 发布，基于 ClickHouse 构建共享代码索引与 Agent Memory。

迁移到 Data Agent：SQL、Query Plan、耗时、失败原因、人工反馈、数据版本均可作为 Memory Event。

07 · ClickHouse 26.10：Query Replay 是升级门禁

11/15 社区发现 ORDER BY LIMIT re-merge sort 内存回归，示例 266MB→1.37GB。

建议：采样 Top SQL + Agent SQL，fingerprint→replay→CPU/Memory/P95/错误率，作为升级门禁。

08 · Flink/Spark/Kafka 本周“不更新”也是信号

本周检索未发现足够高信息密度的核心稳定版发布；Kafka 4.3.2 为 10/23 稳定基线，Spark 当前主线文档为 4.3.0。

判断：本周投资重点应是 Agent 调度、诊断、治理，而非追逐版本号。

8. 本周最值得亲自验证的一件事

Data Agent：本地 SQL System-1 + 强模型 System-2

目标：验证在准确率基本持平时能否降低 P95 与 API 成本。

问题 → Intent/Risk Gate → Local 7B Text-to-SQL ↓ SQL Validator ──低置信度──► Strong LLM ↓ EXPLAIN / Execute ↓ Result + Citation + SQL Trace ↓ Memory / Eval

步骤：500 条真实问题 → 建业务 Schema/Metric context → 本地生成 → 权限/EXPLAIN/执行验证 → 低置信度升级 → 与 baseline 对比。

门槛：Execution Accuracy ≥ baseline 的 95%；同时统计升级率、P95、Token/Query、API 成本、越权率、错误 SQL 率。

预期：若 40%–60% 请求可安全走本地路径且准确率基本持平，值得进入生产化。

数据来源与筛选原则：优先 Apache 官方、GitHub、ClickHouse/Doris 官方工程文章、arXiv 原论文；厂商数字标注为官方/作者报告，不当作独立验证。未发现本周足够高信息密度的 Flink/Spark 核心版本更新，不为凑数虚构变化。Kafka 4.3.2 于 2026-10-23 发布，本期仅作稳定基线。
