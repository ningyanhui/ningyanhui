3. 深度分析

① Airflow 3.4：Agent 进入调度系统

是什么：Airflow 3.4 引入 bounded Task Loops、多语言 DAG，并继续完善 common.ai provider，让 LLM/Agent 成为普通 Airflow task，同时支持 human approval。

核心创新：不是再做一个 Agent Framework，而是把 Agent 放进已有的 DAG、依赖、重试、状态和审批体系。

推荐架构：Agent Planner → Airflow DAG → Policy/Approval → Spark/Flink/Doris Tool → Result/Eval → Audit。

落地边界：Agent 负责计划和低风险决策；资源分配、SQL 白名单、集群操作和发布仍由确定性控制器执行。

PoC：让 Agent 诊断一个 Spark 失败任务，生成修复计划，调用受控 Tool 重跑；指标看成功率、人工介入率、恢复时间和误操作率。

② ClickHouse + Xata：AI 数据平台开始融合状态与分析

事实：11/9 ClickHouse 宣布平台扩展，并收购 Xata；官方定位覆盖 Postgres、Observability、安全和 AI engineering。

为什么重要：Agent 不只是查询分析数据，还需要短生命周期状态、会话、工具结果、trace、evaluation 与业务数据。

推荐架构：OLTP/Agent State → Postgres；事件/Trace → Kafka；分析/评测 → ClickHouse；对象/大模型数据 → Lakehouse；统一 MCP/Policy Gateway。

风险：平台整合不等于架构必须整合；事务一致性、数据驻留、成本模型和供应商锁定仍要独立评估。

③ MCP Servers v2.3：从插件变成平台组件

事实：官方 servers 11/4 发布 v2.3.0，包含 filesystem、memory、git、fetch、time 等包更新。

工程含义：Tool catalog、schema、身份、权限、审计、版本兼容与限流需要统一治理。MCP 2026-07-28 规范已经转向无状态核心、缓存 hints、header routing 和更强授权。

建议：内部不要让 Agent 直连数据库/集群 API；统一经过 Tool Gateway，映射用户/Agent identity，并记录 request→tool→side effect。

④ Pando：Agent 并发正在重塑基础设施

事实：OpenAI 公开 Pando Git backend：通过按分支并行写、packfile 复用、缓存与请求合并，生产 push 中位延迟降低近 80%，服务近 PB Git 数据/日。

可迁移启示：数据平台也可能出现 Agent burst：大量并发 metadata 查询、SQL explain、job submit、log fetch、catalog scan。

建议：在 API Gateway、Catalog、Scheduler 和 OLAP Gateway 做 request coalescing、热点缓存、幂等 token、队列隔离和 workload-aware rate limit。

⑤ SPRING-5：Tool schema 质量要用成本衡量

事实：论文提出 20 个 tool families、344 个任务，以调用次数/成本而不仅是 accuracy 评估文档修复；研究显示批量重写对成本缺口的改善明显高于简单在线自演化。

数据平台启示：一个“看起来正确”的 MCP Tool，如果 schema 让 Agent 多调用 3 次、错误路由一次，就会放大 token、延迟和资源成本。

PoC：为 20 个内部数据平台 Tools 建 schema A/B，统计 calls/correct-task、P95 latency、失败重试率。

⑥ AgentSM：把 SQL Trace 变成长期记忆

核心思路：不是把历史 scratchpad 原样塞进上下文，而是把执行轨迹整理为可复用的结构化语义记忆。论文报告在 Spider 2.0 Lite 上达到 44.8% execution accuracy，并降低平均 token 与 trajectory 长度。

企业落地：保存“问题 → 业务实体 → 表 → SQL → 执行结果 → 人工修正”的结构化 Trace，并按业务域/指标域检索。

风险：错误 SQL 也可能被记忆，因此 Memory 必须带 quality score、owner、数据版本和过期策略。

⑦ HeteroTask：调度优化从静态 profiling 走向在线校准

论文针对 CPU/GPU 异构集群，结合多变体规划、buffer 生命周期建模和 Bayesian optimization 校准运行时开销，在实验环境中获得明显 makespan 改善。

工程启示：对 Data + AI 混合集群，历史平均耗时可能不足以指导 Agent/Scheduler 决策，应把运行时反馈纳入调度模型。

SQL Trace Memory

PoC：将历史问答、SQL、执行计划和人工纠错构建为结构化 memory，比较无 memory / vector memory / semantic trace memory。

指标：execution accuracy、平均 tool calls、token、P95、重复错误率。

P1

Agent Burst Protection

PoC：模拟 100 个 Agent 同时查询 Catalog/SQL Gateway，加入 request coalescing + priority queue + cache。

指标：吞吐、P95/P99、数据库 QPS、缓存命中率、队列等待时间。

8. 本周最值得亲自验证的一件事

1–3 天 PoC：Agent × Airflow × Flink/YARN 故障自愈闭环

  1. 采集 20–50 个历史 Flink/YARN 失败案例，整理错误日志、配置、运行指标与人工修复动作。
  2. 将“查日志、查 Job、查 Kafka lag、查 checkpoint、重跑、修改并行度”封装为只读/低风险/高风险三类 Tools。
  3. 用 Airflow 3.4 common.ai task 驱动 Agent，先只允许诊断和生成修复计划；高风险动作必须人工审批。
  4. 加入 Trace Memory，保存成功修复路径，并在第二轮任务中检索相似案例。
  5. 比较人工处理、普通 Agent、Agent + Memory + Workflow 三种模式。

核心指标：根因分类准确率、MTTR、自动恢复率、错误副作用率、Tool calls/task、LLM token/task、P95 完成时间。

预期结论：如果 Agent + Workflow 能在不提高误操作率的情况下把 MTTR 降低 30% 以上，就值得进一步建设 Data/Ops Agent Control Plane；否则优先补日志、指标、知识和 Tool schema，而不是继续堆模型。

数据来源与筛选原则：优先 Apache/官方项目 Release、官方工程博客、论文与可复现实验；过滤纯营销稿、重复资讯和缺少工程细节的内容。事实与分析判断分开标注；论文实验结果不直接等同生产收益。
