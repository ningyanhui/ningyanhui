3 · 深度分析

3.1 Confluent Managed Model Inference：Flink 直接成为实时 AI 执行层

是什么：把模型调用封装进流计算 SQL，让事件进入 Flink 后直接完成 anomaly detection、LLM explanation、Agent action。

事实：11/18 官方宣布 LLM 与 embedding 模型 GA；示例通过 AI_DETECT_ANOMALIES、AI_COMPLETE 和 AI_RUN_AGENT 形成持续运行链路。

为什么重要：你当前关注的 Flink + Data Governance Agent 正好对应这一架构。真正的工程问题不再是“如何调用模型”，而是如何处理 backpressure、TTFT、checkpoint、幂等、成本、模型超时。

推荐路径：Kafka → Flink State/CEP → 风险 Gate → 本地轻模型 → 高价值事件 LLM → Agent Tool → Kafka/Audit；模型调用必须具备 timeout、circuit breaker、dead-letter 和 idempotency key。

风险：网络模型调用会成为 Flink operator 的尾延迟来源；不要让无限重试拖垮 checkpoint。

PoC：1000 events/s，1% 进入 LLM，比较同步调用、async I/O、批量 inference 三种方式，测 p95/p99、checkpoint duration 和 backlog。

3.2 ClickHouse Loom：值得迁移到 Data Agent 的 Memory 架构

Loom 的关键不是“用 ClickHouse 存向量”，而是把 memory、provenance、version、search、run trace、cost 放在同一个可查询系统。

官方结果：ClickHouse 报告其代码问答 mean answer-quality 从 0.78 提升到 0.84；每条 memory 带来源、置信度、版本和冲突信息。

对 Data Agent 的迁移：不要只建 embedding(text)。建议设计 agent_memory、sql_examples、schema_snapshot、tool_runs、eval_results、memory_conflicts 六类表，并用 SQL 把 Memory Quality 纳入治理。

3.3 Doris + Vane：多模态数据真正进入数仓语义层

这是本期与你现有研究最直接相关的一项。Vane 负责解析音频、图像、视频并生成 transcript / fields / embedding；Doris 将结果和 ticket/order/batch 等结构化数据 Join。

工程判断：这比单独部署“向量数据库 + RAG”更像数据平台能力：原始证据 → AI 派生数据 → 业务主键 → SQL/Vector/Text 检索 → 反查原始证据。

尤其适合客服录音、质检图片、8D/维修文档、设备日志。关键边界是：AI 分类结果必须标记为 candidate，保留 source URI、timestamp、model/version 与 review status。

3.4 Airflow 3.4：Agent 开始进入调度控制平面

Airflow 3.4 的 bounded Task Loops、多语言 DAG Importer 和 AI provider 的 human approval 表明 Agent 不再只是外围 chatbot，而是工作流中的可控执行单元。

推荐边界：Agent 负责 diagnose / plan / propose；Scheduler 负责 dependency / retry / SLA / quota；Executor 负责 resource isolation；Policy Gateway 负责权限。Agent 不直接拥有集群管理员权限。

3.5 MCP 2026-07-28：从“工具协议”变成可扩展服务基础设施

stateless core 让远程 MCP server 可以放在普通 L7 load balancer 后面；header-based routing 让网关能够在模型之外做授权和路由；list response cache hints 则降低工具发现开销。

对 Data Platform 的意义：Data Agent 不应该直连 20 个数据库。应形成 MCP Gateway → Policy → Tool Registry → Doris/Flink/Kafka/Airflow adapters 的统一层。

3.6 Context Bank Governance：Data Agent 的“知识库”也要像数仓一样治理

11/23 的 arXiv 论文把长期积累的 SQL examples / business rules 中互相矛盾的知识称为 context-bank rot。其结论非常适合企业 Data Agent：单条 example 正确，不代表集合一致。

落地：给每个 example 增加 owner、version、effective_time、source_query、semantic_contract、last_eval；每天做 contradiction scan；线上 retrieval 只使用 active + compatible 的知识。

8 · 本周最值得亲自验证的一件事

PoC：Data Agent 的“轻模型门控 + SQL Memory + 强模型兜底”

  1. 准备 300–500 条真实历史 SQL/自然语言问题，按 easy/medium/hard 分层。
  2. 建立 SQL Memory：问题、SQL、Schema、执行结果摘要、owner、版本、eval score。
  3. 先做 retrieval：相似问题 + schema + business definition。
  4. 轻模型生成 SQL；SQL parser + EXPLAIN + read-only policy 做 gate。
  5. 低置信度或执行失败才升级强模型。
  6. 把成功 SQL 与人工反馈写回 Memory，但只允许通过 eval gate 的样本进入 active 集合。
Question ↓ Intent / Permission ↓ Memory Retrieval ───────┐ ↓ │ Local SQL Model │ ↓ │ SQL AST + EXPLAIN │ ├── pass → Execute → Result → Eval └── fail → Strong LLM → Verify → Execute ↓ Memory Update

3 天验收线：Execution Accuracy ≥ baseline；P95 延迟下降 ≥30%；强模型升级率 ≤60%；错误 SQL 被 policy/EXPLAIN 拦截 ≥95%；Memory 命中请求 token 成本下降 ≥25%。达不到就不要生产化，继续优化 schema retrieval 和 semantic definitions。
