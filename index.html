03 / 深度分析

01 / DEEP DIVE

Doris 原生 Delta Lake 读取

技术与本周变化：把 Delta 纳入 Doris Catalog 访问路径；当前是社区进展，不能等同稳定版 GA。

核心创新 / 平台关联：减少 Spark 预转换与额外副本。

推荐架构：Delta Lake → Doris Catalog → Query Gateway → Data Agent。

依赖条件：版本支持、Catalog 权限、对象存储访问。

风险与限制：协议兼容、Schema Evolution、删除向量和快照语义。

预期收益（待测）：潜在减少数据复制与 ETL 维护，收益待测。

PoC：100 张表、10 种 Schema 变更、50 条 SQL 对照 Spark。

02 / DEEP DIVE

Doris 行级 TTL

技术与本周变化：面向明细行的自动过期机制；本周社区报告列为落地项。

核心创新 / 平台关联：将 Trace、事件、检索缓存生命周期交给存储层。

推荐架构：Kafka/Flink → Doris Trace Table → TTL → Agent Eval。

依赖条件：确认目标版本及 TTL 条件表达式。

风险与限制：删除延迟、存储回收、查询一致性。

预期收益（待测）：潜在降低人工清理与存储成本。

PoC：1M 行、不同 TTL、监测清理延迟及查询结果。

08 / 本周最值得亲自验证的一件事

1–3 天 PoC：Doris + Agent Trace 的生命周期与查询性能

目标：验证高频 Agent 轨迹在 Doris 中是否能低成本存储、检索和自动过期，同时保留必要的审计证据。

Day 1：合成 100 万条 Trace（task_id、tool、SQL hash、token、latency、result、timestamp），确认目标 Doris 版本的 TTL 支持。

Day 2：测试按任务/工具聚合、异常检索、过期数据查询，观察 P95/P99、磁盘占用与 TTL 回收。

Day 3：注入写入失败、重复事件、时钟偏移；验证幂等、保留期和审计完整性。

验收门槛（建议）：Trace 查询 P95 < 500ms；审计关键事件保留率 100%；过期数据回收延迟与存储成本均有量化结果。若目标版本未提供行级 TTL，先用分区生命周期策略作基线，不应假定功能可用。

数据来源与筛选原则

优先项目官方社区报告、技术博客与公开工程案例；事实、官方声称和本文工程判断分别标注。未将未合并 PR 视为正式 GA；未将厂商案例直接视为可复制收益。本期没有足够新的 Flink、Spark、Kafka 核心发布，不为凑数重复旧版本。
